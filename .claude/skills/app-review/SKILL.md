# アプリ多角レビュー

このアプリ（これ食っていい）を一通り見て、**優先順位を付けた改善案**を出す。

`/code-review` がコードの正しさを見るのに対し、こちらは**使う人の視点**が主。両方の観点が必要なので、どちらか一方では足りない。

## 対象

`index.html` / `src/main.js` / `src/style.css` / `public/sw.js` / `public/manifest.json`。

ユーザーが画面名（判定・今日の収支・設定）を指定したら、その範囲に絞る。

## 見る観点

必ず6つ全部に目を通す。該当なしなら「問題なし」と書く。**観点を勝手に減らさない。**

### 1. 使い勝手（最優先）

スマホを片手で持って操作する前提で見る。

- 一番よく使う操作が、最初の画面から何タップで届くか
- タップ領域が小さすぎないか（目安 44×44px 以上）
- 押した後に反応があるか（無反応だと連打される）
- 入力欄の `inputmode` や `type` が内容に合っているか（数字入力でキーボードが英字だとつらい）
- エラーが出たとき、次に何をすればいいか書いてあるか
- 読み込み中だと分かるか

### 2. 画面と文言

- 文字が小さすぎないか、コントラストが足りているか
- 専門用語がそのまま出ていないか（ユーザーは非エンジニア。他の人が使う可能性もある）
- 数字に単位が付いているか
- 空っぽの状態（記録ゼロ、初回起動）で画面が寂しくないか、次の行動が示されているか
- 横幅の狭い端末（375px程度）で崩れないか

### 3. 機能

- **足りない機能**より先に、**使われていない機能**を疑う。画面が複雑になるほど使いにくくなる
- 間違えたときに取り消せるか（削除・記録の取り消し）
- データを失う操作に確認があるか
- 同じ情報を2回入力させていないか

### 4. 表示速度とオフライン

- 起動時に取得するデータ量が増え続ける作りになっていないか
- 画像をそのまま送っていないか（縮小してから送る）
- 電波が悪いとき・圏外のときに何が起きるか
- Service Worker のキャッシュ対象に、存在しないファイルが混ざっていないか（1つでも404だと`addAll`がまるごと失敗してオフライン機能が死ぬ）
- アプリを更新したとき、スマホ側に反映されるか

### 5. 安全まわり

- APIキーが端末内(localStorage)に留まっていて、どこにも送信・同期されていないか
- 個人データ（体重、食事など）が他人から見えない作りか
- 外部に送る通信が、必要なものだけか

### 6. コードの健全性

- 1つの関数が長くなりすぎていないか
- 同じ処理のコピペが増えていないか
- 今後の機能追加でつまずきそうな箇所はどこか

## 手順

1. 対象アプリのファイルを**全部読む**（HTML・CSS・JS・sw.js・manifest.json）。読まずに推測で書かない
2. 上の6観点で気になった点を洗い出す
3. **実際に壊れているものと、好みの問題を分ける**
4. 優先順位を付ける
5. 出力形式にまとめる

## 出力形式

```
## 結論
（3行以内。一番直すべきことは何か）

## 今すぐ直したいもの
（壊れている・データを失う・使えない。ファイルと行番号付き）

## 直すと効果が大きいもの
（動いてはいるが、使い勝手が明確に良くなる）

## 余裕があれば
（好みの範囲、将来の備え）

## 良くできている点
（維持すべき判断。消さないために書く）
```

## 守ること

- **1回の提案は多くて7個まで。** 全部出すと結局どれもやらない
- 各提案に「なぜそれが問題か」を1行付ける。理由がないと判断できない
- **推測で「壊れている」と書かない。** コードのどこがそうなっているか示せないものは「余裕があれば」に置く
- この場で直さない。**提案までで一度止めて、どれをやるか選んでもらう**
- 専門用語を使うときは、その場でカッコ書きで説明する
